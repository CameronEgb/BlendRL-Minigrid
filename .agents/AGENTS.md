## 1. Project Overview & AI Agent SOP (PRIME DIRECTIVE)
BlendRL jointly learns symbolic (logic) and neural policies. It integrates logic agents (NSFR/Neumann) with RL (PPO, IQL) to create hybrid agents.

> [!CAUTION] 
> **AI PRIME DIRECTIVE - ZERO TOLERANCE FOR HACK SCRIPTS**
> As an AI agent working in this repository, you are strictly forbidden from writing standalone `if __name__ == "__main__":` python scripts, bash scripts, or one-off "hack" files in the root or `scripts/` directories to accomplish tasks. 
> 
> You MUST use the modular pipeline architecture:
> 1. **To run experiments:** Use `python run_pipeline.py <group>/<exp>` and configure via Hydra in `in/config/`.
> 2. **To add new plotters:** Subclass `BasePlotter` in `plot/` and add it to `default_plots:` in the environment's `_base.yaml`.
> 3. **To add new agents/methods:** Subclass `BaseAgent` in `src/methods/`, decorate with `@register_agent`, and add it to `src/method_registry.py`.
> 4. **To add new pipeline workflows:** Create a new module in `src/pipeline/` and decorate your runner with `@register_task`.
> 
> See the corresponding `.agents/skills/` for exact instructions on these operations. Temporary debugging scripts are ONLY permitted in `<Artifact Directory>/scratch/`.

## 2. The Golden Rule of Comparison
The ultimate objective of this codebase is to compare **Online** vs. **Offline** learning efficiency.
- **The Rule:** For any data point (x-value) on a comparison plot, the Offline agent must be trained *only* on the exact dataset generated by the Online agent up to that same x-value.
- **X-Axis:** Represented by the number of steps/transitions in the database.
- **Interval Logic:** `INTERVALS_COUNT` defines snapshot points. 
- **Evaluation Standard:** For interactive environments with simulators (e.g. CartPole, Seaquest), interval evaluation points are calculated as a **100-episode average reward** in the online simulator.
- **MIMIC / Pyrenees / Offline-Only Environments:** For static datasets without an online simulator:
  - **`intervals_count` MUST be 1.** Setting it higher restricts the dataset reader to progressive fractional slices — which is only for online-to-offline data-scaling comparisons.
  - **Training length** = `epochs_per_interval` gradient epochs on the full training split.
  - **`eval_episodes` is NOT used.** Simulated gym rollouts on static dataset rows are disabled because policy actions do not alter historical trajectories or patient outcomes.
  - **Validation Architecture:** Datasets are partitioned into train and validation splits (e.g. 90/10 by trajectory/patient ID). Lightning computes real validation metrics (`val/loss`, `val/bellman_loss`, `val/cql_loss`, `val/q_loss`).
  - **Checkpointing & Tuning:** `ModelCheckpoint` monitors `"val/loss"` (`mode="min"`). Optuna sweeps minimize `"val/loss"`.
  - **`total_timesteps`** = automatically inferred (`total_timesteps: auto`) at runtime from `len(dataset)`.
  - **Downstream Clinical Metrics:** Post-training clinical evaluation (AUC, precision-recall, lead times) is handled by task evaluation scripts (such as `src/early_prediction/eval.py`).

## 3. Execution Pipeline & Configuration
The project uses a modular configuration system powered by Hydra.

### Modular Specification
- **Configuration:** All experiment parameters (hyperparameters, environment, methods) are defined in YAML files located in `in/config/`.
- **Precedence:** CLI arguments > experiment YAML > group `_base.yaml` > env/mode/site defaults > `config.yaml` root defaults.
- **Entry Point:** `python run_pipeline.py <experiment_name> [optional Hydra overrides]` is the **sole** entry point for all experiments.
- **Task Registry:** `run_pipeline.py` dispatches to task runners via `src/pipeline/task_registry.py`. New tasks auto-register with `@register_task("name")`. Default task is `"rl"` (standard online/offline training). Other registered tasks: `early_prediction`, `reciprocal_refinement`.
- **Dynamic Orchestration:** `run_pipeline.py` reads `online_methods` and `offline_methods` from the experiment config. It executes each online method sequentially, then each offline method (defaulting to the dataset generated by the first online method).

### Declarative Environment Config Keys
Environment YAML files (`in/config/env/*.yaml`) define behavior declaratively — no hardcoded env-name string checks in Python:
- `offline_only: true/false` — Whether the env lacks an online simulator (mimic, pyrenees = true)
- `monitor_metric: "val/loss"` or `"eval/reward"` — What metric to monitor for checkpointing/tuning
- `preprocess_on_load: true/false` — Whether the dataset needs preprocessing when loaded (pyrenees = true)
- `default_plots: [...]` — Which plotters to run by default for this environment

### Cluster Resources in Config
Experiment configs can specify cluster resource requirements under a `resources:` block:
```yaml
resources:
  time: "04:00:00"
  gpus: 1
  cores: 16
  memory: "32G"
```
Priority: CLI flags > experiment `resources:` > site config > hardcoded fallbacks.

### Dataset & Experiment Mapping
- **Experiment ID & Group:** Automatically inferred from the experiment YAML's file path (`in/config/experiment/<group>/<experiment_id>.yaml`) or overridden via CLI (`-e <exp_id>`). They no longer need to be explicitly written in the YAML configs.
- **Method Lists:**
    - `online_methods`: Comma-separated list of agents to run in `online` mode. Supports hierarchical paths (e.g., `ppo/cp_tuned,blendrl/cp_tuned`).
    - `offline_methods`: Comma-separated list of agents to run in `offline` mode (e.g., `iql/cp_tuned,blendrl_iql/cp_tuned`).
    - `offline_datasets`: (Optional) Comma-separated list of dataset names (can use hierarchical paths like `ppo/cp_tuned`).
        - **Internal Normalization:** Slashes in method names are converted to underscores (e.g., `ppo/cp_tuned` -> `ppo_cp_tuned`) for log and dataset directory names to ensure consistency.
        - **Many-to-Many Execution:** For every dataset listed in `offline_datasets`, the pipeline will execute *all* methods listed in `offline_methods`.
        - If a dataset name matches an `online_method` in the same run, the pipeline uses the dataset generated by that method.
        - Otherwise, it searches for an existing dataset in `results/datasets/[GROUP]/[EXP_ID]/[NORMALIZED_NAME]`.
        - If no matching dataset is found, the pipeline exits.
        - Default: If omitted, all offline methods run against the datasets generated by all `online_methods`.
- **Standard Paths:**
    - Experiments/Logs: `results/logs/[GROUP]/[EXP_ID]/[AGENT]`
    - Datasets: `results/datasets/[GROUP]/[EXP_ID]/[AGENT]`
- **Auto-Plotting:** `run_pipeline.py` automatically triggers `plot/manager.py` at the end of the cycle unless `no_plot=true` is passed.
- **Plots:** Saved in `results/plots/[GROUP]/[EXP_ID]/`.

## 4. Data Saving & Dataset Schema
- **Writer Logic:** The `DatasetWriter` (`src/dataset_utils.py`) serializes transitions during Online Phase 1.
- **Compression & Efficiency:** 
    - Observations are converted to `uint8` (for images) or `float32` (for vectors) on the CPU before saving to minimize VRAM and disk usage.
    - Transitions are saved in chunked `.pkl` files (default `chunk_size=100,000`) in `results/datasets/[GROUP]/[EXP_ID]/[AGENT]/`.
- **Dataset Manifest:** `DatasetWriter.close()` writes a `dataset_manifest.json` to the dataset directory containing: generator agent, experiment ID, group, env name, seed, total transitions, chunk count, creation timestamp (ISO-8601), git commit, branch, and dirty flag.
- **Transition Schema:** Each transition is a dictionary:
    - `obs` / `next_obs`: Neural input.
    - `logic_obs` / `next_logic_obs`: Symbolic input (if using hybrid agents).
    - `action`, `reward`, `done`: Standard RL transition data.
- **Downstream Usage:** `RLDataModule` (`src/data/rl_data_module.py`) reads these chunks to create the offline replay buffer.

## 5. Operational Challenges & Environment
- **Site Profiles & Execution Modes (`site`):** 
    - **Interactive / Local CLI (`site=local`, Default):** `run_pipeline.py` defaults to interactive command-line execution (`site=local`), running experiments as standard subprocesses. Use this on your local machine or interactively on a cluster compute node (`salloc` / `srun`).
    - **Slurm Cluster Batch (`site=ncshare`, `site=arc`):** Generates and submits Slurm batch scripts using site-specific partition, module load, and resource configurations.
    - **Cluster Push Mandate:** Whenever recommending or generating a command to submit to the cluster (e.g., `site=ncshare` or `site=arc`), the agent MUST push changes to GitHub so the codebase is ready to be pulled and run on the cluster.
- **Filesystem Storage Rules:**
    - `/mnt/beegfs/` is **slow** bulk network storage and MUST NEVER be used for active training, dataset loading, or fallback resolution paths.
    - All datasets and training workloads must strictly execute from repository paths (`in/datasets/`) or local user storage (`/hpc/home/`).
- **State Recovery:** For long Atari runs (e.g., Seaquest), use the `recover=true` Hydra override to resume training from the latest checkpoint. Training states are saved at evaluation intervals in `results/checkpoints/[GROUP]/[EXP_ID]/[AGENT]/`.

## 6. Hydra & Debugging Heuristics
- **Hydra Outputs:** Every run generates a timestamped directory in `results/hydra/outputs/YYYY-MM-DD/HH-MM-SS/` containing the exact `.hydra/config.yaml` and logs for that specific execution.
- **Debugging Failures:** 
    - **Primary Resource:** `results/logs/[GROUP]/[EXP_ID]/[AGENT]/version_X/` contains `metrics.csv` and TensorBoard events.
    - **Configuration Audit:** Check the `.hydra/config.yaml` in the `results/hydra/outputs/` folder for the specific run.
- **Rule Changes vs. Code Changes:** 
    1. Check if the rules work in other environments. If they do, focus on the environment-specific valuation code.
    2. **MANDATE:** **Always ASK** before modifying logic rules (`in/rules/[env]/[ruleset]/`). Prioritize fixing Python code unless the rules are fundamentally flawed for that specific task.
- **Surgical Updates:** Do not refactor unrelated code.
- **Verification:** Ensure `run_pipeline.py` orchestration is never broken and that `src/train.py` remains compatible with Hydra.

## 7. Unified Logging & Reproducibility
- **Dual Loggers:** The project uses `CSVLogger` for data analysis and `TensorBoardLogger` for real-time monitoring.
- **Metrics Source:** `results/logs/[GROUP]/[EXP_ID]/[AGENT]/version_X/metrics.csv` is the foundational file for all plotting.
- **Alignment Metric:** The `transitions` column is the universal x-axis. It ensures that Online (PPO) and Offline (IQL/BlendRL) agents are compared at the exact same data exposure levels.
- **Reproducibility Metadata (`src/core/metadata.py`):** Every training run automatically captures:
    - **Git Provenance:** Commit SHA, branch, dirty flag. If the tree is dirty, `git diff HEAD` is saved as `git_patch.diff` alongside checkpoints.
    - **System Info:** Hostname, OS, Python version, PyTorch version, CUDA version.
    - **CLI Command:** The exact `sys.argv` that launched the run.
    - **Seed:** From `cfg.seed`.
- **`runtime.json`:** Written by `finalize_training()` in `src/core/lightning_builder.py` to both checkpoint and log directories. Contains: agent, experiment_id, group, training_time_seconds, start/end timestamps (both POSIX and ISO-8601), GPU stats, git provenance, system info, seed, CLI command, and Hydra output directory path.
- **Hydra Overrides:** `.hydra/overrides.yaml` is automatically copied into `results/logs/[GROUP]/[EXP_ID]/[AGENT]/version_X/` so the exact CLI flags are co-located with experiment results.

## 8. Environment Customization & Wrappers
- **Standardized Interface:** All environments are wrapped using `VectorizedNudgeBaseEnv` (`src/blendrl/env_vectorized.py`).
- **Evaluation:** Handled by the `EnvironmentEvaluatorCallback` (`src/utils.py`). It executes a fixed number of episodes (default 100) at set transition intervals, ensuring statistical rigor across all agent types.
- **Environment Rules:** Found in `in/envs/[ENV]/`, which may include custom reward shaping (`blenderl_reward.py`) or architecture definitions (`mlp.py`).

## 9. Agent Implementation Guide
Agents are implemented as PyTorch Lightning Modules in `src/methods/`:
- `PPOAgent`: Standard online actor-critic RL.
- `IQLAgent`: Offline RL using Implicit Q-Learning.
- `BlendRLAgent` / `BlendRLIQLAgent`: Hybrid agents that bridge symbolic logic and neural networks.
- **Architecture Selection:** `get_neural_agent` (`src/utils.py`) dynamically selects between CNN and MLP architectures based on the environment configuration.

## 10. Logic-Neural Bridge (The "Blender")
- **Reasoners:** The symbolic backbone uses either **NSFR** (Neural Symbolic Forward Reasoner) or **Neumann**.
- **Rule Loading:** `get_blender` (`src/utils.py`) initializes the logic reasoner using the predicate and clause definitions in `in/rules/`.
- **Hybrid Forward Pass:** Hybrid agents process raw observations through neural encoders and logic reasoners simultaneously, blending their outputs into a single policy.

## 13. Plotting Architecture
- **Auto-Discovery:** `plot/manager.py` auto-discovers plotters by scanning `plot/` for `BasePlotter` subclasses. No manual registry needed.
- **Adding a New Plotter:** Create `plot/my_plotter.py` with a class subclassing `BasePlotter`, set `self.name` in `__init__`, implement `run()`. Optionally create `plot/_my_plotter_config.yaml` for defaults.
- **Environment Defaults:** Default plots per environment are defined in `in/config/env/*.yaml` under `default_plots:`. Experiments override via `plots:` in their YAML.
- **Config Resolution:** Plotters first read the saved `config.yaml` from `results/logs/` or `results/checkpoints/` (the exact config the trainer used), falling back to parsing the experiment YAML for experiments that haven't been run yet.
- **Shared Plotting:** `BasePlotter.plot_metric_series()` handles multi-method metric plotting with multi-version mean±SEM. Used by `ConvergencePlotter` and `LossesPlotter`.

## 14. Pipeline Architecture (`run_pipeline.py` & `src/pipeline/`)
- **Thin Orchestrator:** `run_pipeline.py` is a lightweight entry point that validates configs and dispatches to task runners via the task registry:
    - **`src/pipeline/task_registry.py`**: `@register_task("name")` decorator pattern for auto-discovered task runners. `get_task(name)` resolves using longest-prefix matching.
    - **`src/pipeline/config.py`**: Name normalization (`normalize_agent_name`), method list parsing (`parse_method_list`), and CLI extra-argument sanitization (`filter_pipeline_args`).
    - **`src/pipeline/datasets.py`**: Dataset path resolution (`resolve_dataset_path`), online dataset symlinking (`ensure_online_dataset_path`), experiment runners, and plotting dispatch.
    - **`src/pipeline/slurm.py`**: Centralized Slurm header builder (`generate_sbatch_header`) with unified `--mail-type=END,FAIL` and `--mail-user=cegbert@ncsu.edu` configuration, and job submission (`submit_sbatch`). Accepts `resources` dict from experiment configs.
    - **`src/pipeline/local_runner.py`**: Local sequential execution for online & offline RL phases.
    - **`src/pipeline/slurm_runner.py`**: Remote Slurm cluster batch script generation and job dependency orchestration.
    - **`src/pipeline/early_prediction_task.py`**: Standalone early prediction sweeps, checkpoint evaluations, and Optuna tuning. Registered as `@register_task("early_prediction")`.
    - **`src/pipeline/reciprocal_task.py`**: Iterative EP ↔ CQL co-training orchestration (`run_reciprocal_refinement`). Registered as `@register_task("reciprocal_refinement")`.
    - **`src/pipeline/optuna_utils.py`**: SQLite URL constants (`DEFAULT_OPTUNA_DB_URL`), Optuna study management, and background dashboard launching.
    - **`src/pipeline/validation.py`**: Pre-flight validation checks for environment configs, sweep parameters, and offline-only dataset constraints.

## 15. Reciprocal Refinement (EP ↔ CQL Co-Training)
- **Concept:** The EP septic shock predictor and CQL offline RL policy iteratively improve each other. EP provides reward shaping for CQL; CQL provides V(s) features for EP.
- **Reward Shaping Module:** `src/reward_shaping.py` implements potential-based reward shaping (Ng et al. 1999):
    - Φ(s) = −P_EP(shock | observation window ending at s)
    - r_shaped = r_TQN + λ * (γ * Φ(s') − Φ(s))
    - Provably preserves optimal policies — EP can only accelerate convergence, never bias CQL.
- **Reward Shaping Config:** Parameters are defined in `in/config/env/mimic.yaml` under `reward_shaping:` (ckpt_dir, lambda, gamma, window, arch, cql_ckpt). The module reads from `cfg.env.reward_shaping` with `os.environ` fallback for backward compatibility.
- **Reward Type:** Set `reward_type: ep_shaped` in env config to activate. This applies TQN base rewards + EP potential shaping via `in/envs/mimic/hooks.py`.
- **Pipeline Task:** `task: reciprocal_refinement` in experiment YAML. Orchestrated by `src/pipeline/reciprocal_task.py`.
- **Experiment Config:** `in/config/experiment/mimic/reciprocal_refinement.yaml`
- **Results:** Per-round checkpoints in `results/checkpoints/[GROUP]/[EXP_ID]/roundN/`, convergence log in `results/plots/[GROUP]/[EXP_ID]/convergence_log.json`.
