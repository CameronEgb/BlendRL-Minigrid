## 1. Project Overview
BlendRL jointly learns symbolic (logic) and neural policies. It integrates logic agents (NSFR/Neumann) with RL (PPO, IQL) to create hybrid agents.

## 2. The Golden Rule of Comparison
The ultimate objective of this codebase is to compare **Online** vs. **Offline** learning efficiency.
- **The Rule:** For any data point (x-value) on a comparison plot, the Offline agent must be trained *only* on the exact dataset generated by the Online agent up to that same x-value.
- **X-Axis:** Represented by the number of steps/transitions in the database.
- **Interval Logic:** `INTERVALS_COUNT` defines snapshot points. 
- **Evaluation Standard:** All interval evaluation points (both online and offline) MUST be calculated as a **100-episode average reward** to ensure statistical significance.
- **MIMIC/Offline-Only Exception:** For offline-only environments (such as MIMIC) where an online simulator does not exist, the pipeline runs purely in offline mode on the static dataset, and the Online vs. Offline comparison rules do not apply.

## 3. Execution Pipeline & Configuration
The project uses a modular configuration system powered by Hydra.

### Modular Specification
- **Configuration:** All experiment parameters (hyperparameters, environment, methods) are defined in YAML files located in `in/config/`.
- **Precedence:** CLI arguments > YAML config > Defaults. This allows overriding specific values from a base YAML template using Hydra syntax (e.g., `agent.lr=0.001`).
- **Entry Point:** Use `python run_pipeline.py <experiment_name>` to run the experiment cycle.
- **Dynamic Orchestration:** `run_pipeline.py` reads `online_methods` and `offline_methods` from the experiment config. It executes each online method sequentially, then each offline method (defaulting to the dataset generated by the first online method).

### Dataset & Experiment Mapping
- **Experiment ID:** Set in the experiment YAML file or overridden via CLI.
- **Method Lists:**
    - `online_methods`: Comma-separated list of agents to run in `online` mode. Supports hierarchical paths (e.g., `ppo/cp_tuned,blendrl/cp_tuned`).
    - `offline_methods`: Comma-separated list of agents to run in `offline` mode (e.g., `iql/cp_tuned,blendrl_iql/cp_tuned`).
    - `offline_datasets`: (Optional) Comma-separated list of dataset names (can use hierarchical paths like `ppo/cp_tuned`).
        - **Internal Normalization:** Slashes in method names are converted to underscores (e.g., `ppo/cp_tuned` -> `ppo_cp_tuned`) for log and dataset directory names to ensure consistency.
        - **Many-to-Many Execution:** For every dataset listed in `offline_datasets`, the pipeline will execute *all* methods listed in `offline_methods`.
        - If a dataset name matches an `online_method` in the same run, the pipeline uses the dataset generated by that method.
        - Otherwise, it searches for an existing dataset in `results/datasets/[GROUP]/[EXP_ID]/[NORMALIZED_NAME]`.
        - If no matching dataset is found, the pipeline exits.
        - Default: If omitted, all offline methods run against the datasets generated by all `online_methods`.
- **Standard Paths:**
    - Experiments/Logs: `results/logs/[GROUP]/[EXP_ID]/[AGENT]`
    - Datasets: `results/datasets/[GROUP]/[EXP_ID]/[AGENT]`
- **Auto-Plotting:** `run_pipeline.py` automatically triggers `plot_results.py` at the end of the cycle unless `--no-plot` is passed.
- **Plots:** Saved in `results/plots/[GROUP]/[EXP_ID]/`.

## 4. Data Saving & Dataset Schema
- **Writer Logic:** The `DatasetWriter` (`src/dataset_utils.py`) serializes transitions during Online Phase 1.
- **Compression & Efficiency:** 
    - Observations are converted to `uint8` (for images) or `float32` (for vectors) on the CPU before saving to minimize VRAM and disk usage.
    - Transitions are saved in chunked `.pkl` files (default `chunk_size=100,000`) in `results/datasets/[GROUP]/[EXP_ID]/[AGENT]/`.
- **Transition Schema:** Each transition is a dictionary:
    - `obs` / `next_obs`: Neural input.
    - `logic_obs` / `next_logic_obs`: Symbolic input (if using hybrid agents).
    - `action`, `reward`, `done`: Standard RL transition data.
- **Downstream Usage:** `RLDataModule` (`src/data/rl_data_module.py`) reads these chunks to create the offline replay buffer.

## 5. Operational Challenges & Environment
- **Execution Mode (`--local`):** 
    - **Local (Default):** `run_pipeline.py` defaults to local execution (`--local=True`), running experiments as standard subprocesses.
    - **Cluster:** Historically used for Slurm (`sbatch`) job submission.
- **State Recovery:** For long Atari runs (e.g., Seaquest), use the `recover=true` Hydra override to resume training from the latest checkpoint. Training states are saved at evaluation intervals in `results/checkpoints/[GROUP]/[EXP_ID]/[AGENT]/`.

## 6. Hydra & Debugging Heuristics
- **Hydra Outputs:** Every run generates a timestamped directory in `outputs/YYYY-MM-DD/HH-MM-SS/` containing the exact `.hydra/config.yaml` and logs for that specific execution.
- **Debugging Failures:** 
    - **Primary Resource:** `results/logs/[GROUP]/[EXP_ID]/[AGENT]/version_X/` contains `metrics.csv` and TensorBoard events.
    - **Configuration Audit:** Check the `.hydra/config.yaml` in the `outputs/` folder for the specific run.
- **Rule Changes vs. Code Changes:** 
    1. Check if the rules work in other environments. If they do, focus on the environment-specific valuation code.
    2. **MANDATE:** **Always ASK** before modifying logic rules (`in/rules/[env]/[ruleset]/`). Prioritize fixing Python code unless the rules are fundamentally flawed for that specific task.
- **Surgical Updates:** Do not refactor unrelated code.
- **Verification:** Ensure `run_pipeline.py` orchestration is never broken and that `train.py` remains compatible with Hydra.

## 7. Unified Logging Architecture
- **Dual Loggers:** The project uses `CSVLogger` for data analysis and `TensorBoardLogger` for real-time monitoring.
- **Metrics Source:** `results/logs/[GROUP]/[EXP_ID]/[AGENT]/version_X/metrics.csv` is the foundational file for all plotting.
- **Alignment Metric:** The `transitions` column is the universal x-axis. It ensures that Online (PPO) and Offline (IQL/BlendRL) agents are compared at the exact same data exposure levels.

## 8. Environment Customization & Wrappers
- **Standardized Interface:** All environments are wrapped using `VectorizedNudgeBaseEnv` (`src/blendrl/env_vectorized.py`).
- **Evaluation:** Handled by the `EnvironmentEvaluatorCallback` (`src/utils.py`). It executes a fixed number of episodes (default 100) at set transition intervals, ensuring statistical rigor across all agent types.
- **Environment Rules:** Found in `in/envs/[ENV]/`, which may include custom reward shaping (`blenderl_reward.py`) or architecture definitions (`mlp.py`).

## 9. Agent Implementation Guide
Agents are implemented as PyTorch Lightning Modules in `src/methods/`:
- `PPOAgent`: Standard online actor-critic RL.
- `IQLAgent`: Offline RL using Implicit Q-Learning.
- `BlendRLAgent` / `BlendRLIQLAgent`: Hybrid agents that bridge symbolic logic and neural networks.
- **Architecture Selection:** `get_neural_agent` (`src/utils.py`) dynamically selects between CNN and MLP architectures based on the environment configuration.

## 10. Logic-Neural Bridge (The "Blender")
- **Reasoners:** The symbolic backbone uses either **NSFR** (Neural Symbolic Forward Reasoner) or **Neumann**.
- **Rule Loading:** `get_blender` (`src/utils.py`) initializes the logic reasoner using the predicate and clause definitions in `in/rules/`.
- **Hybrid Forward Pass:** Hybrid agents process raw observations through neural encoders and logic reasoners simultaneously, blending their outputs into a single policy.

## 12. Modular Plot Generation & Custom Styles
Visualizations are auto-generated by the modular framework in `plot/manager.py`, which reads CSV logs from `results/logs/[GROUP]/[EXP_ID]/[AGENT]/version_X/metrics.csv`.

### Modular Architecture (`plot/`)
- `plot/manager.py`: Entry-point orchestrator auto-dispatched by `run_pipeline.py`.
- `plot/base.py`: Base plotter providing hierarchical config merging (`_config.yaml` default < experiment YAML `plots` section < CLI args).
- `plot/convergence.py` (`_convergence_config.yaml`): Convergence curves (`eval/reward`, `train/reward`, `train/length`).
- `plot/losses.py` (`_losses_config.yaml`): Loss curves with per-metric filtering (`losses/actor_loss`, `losses/q_loss`, etc.).
- `plot/reports.py` (`_reports_config.yaml`): Markdown hyperparameter and method comparison tables.

### Plot Commands

python3 plot/manager.py cp_final

# Run specific plotter standalone with CLI overrides
python3 plot/losses.py cp_final --metrics losses/q_loss losses/actor_loss --window 20

# Run convergence plotter standalone
python3 plot/convergence.py cp_final --window 15 --dpi 300
```
python plot_results.py --sources in/config/plot_sources/demo_mc.yaml

### Specifying Versions in Sources (`in/config/plot_sources/`)
In your sources YAML config, you can specify exactly which versions to plot using the `version` key. It supports integers, strings, or a list of versions to compare side-by-side:
```yaml
runs:
  - path: "results/logs/ungrouped/cp_final/ppo_cp_tuned"
    label: "PPO (v0 vs v1)"
    version: [0, 1]  # Load version_0 and version_1 of this method
  - path: "results/logs/ungrouped/cp_final/blendrl_cp_tuned"
    label: "BlendRL (Latest)"
    version: 3       # Load only version_3
```

### Style Configurations (`in/config/plot_styles/`)
You can define custom plotting formats in YAML files. Each entry in the `plots` list supports:
*   `metric`: The exact column name in `metrics.csv` to plot (e.g., `eval/reward`, `losses/q_loss`).
*   `split_by`: *(Optional)* Attribute to split runs into separate plot files (e.g., `source` to split by offline dataset source).
*   `title`: The title template, supporting `{split_value}` and `{experiment}` placeholders.
*   `filename`: Output filename template, supporting `{split_value}` and `{experiment}`.
*   `window`: Rolling average window size for smoothing curves (e.g., `20`).
*   `x_axis`: Column to map to the X-axis (`transitions` or `step` / `epoch`).
*   `xlabel`: Legend name for the X-axis.

## 13. Adding Custom Methods & Architectures

### Adding a Custom Training Method (Agent)
Agents are modular PyTorch Lightning Modules situated in `src/methods/`. To implement a new agent:

1.  **Create the Agent Script**: Create `src/methods/my_new_agent.py` subclassing `PPOAgent` or `lightning.LightningModule`. Ensure you implement:
    *   `training_step(self, batch, batch_idx)`: Sample transitions from the offline data reader via `self.trainer.datamodule.reader.sample(self.cfg.agent.batch_size)` and apply your gradient update manual pipeline (`self.manual_backward()`, `optimizer.step()`).
    *   `get_action_and_value(self, obs, logic_obs=None, action=None)`: Used during evaluation steps.
    *   `configure_optimizers(self)`: Return your model's optimizers.
2.  **Register the Agent**: Open [train.py](file:///Users/cameronegbert/Documents/NCSU/Research/NeSyRL/train.py) and import your agent. Register it in the `main()` function:
    ```python
    elif base_algo_name.startswith("my_new_agent"):
        from src.methods.my_new_agent import MyNewAgent
        model = MyNewAgent(cfg)
    ```
3.  **Define Hyperparameters**: Create a configuration file `in/config/agent/my_new_agent.yaml` to specify default parameters (e.g., learning rates, batch sizes).

### Adding a Custom Architecture
Neural architectures are instantiated via `get_neural_agent` in `src/utils.py`.
*   **Vector Environments (MLP)**: If the environment config specifies `architecture: mlp`, the selection loader checks for the existence of `in/envs/[env_name]/mlp.py`. Place your customized neural network class (`MLP`) in that file. If it doesn't exist, it will fallback to the generic architecture.
*   **Image Environments (CNN)**: Default CNN actors (`CNNActor`) are loaded automatically when no environment-specific architecture is provided.

## 14. Specifying Experiments (Hydra Configurations)

Experiments are structured hierarchically under `in/config/`:
*   `in/config/config.yaml`: The base configuration file defining defaults, paths, and SLURM defaults.
*   `in/config/agent/`, `in/config/env/`, `in/config/mode/`: Directory-specific defaults for algorithms, environments, and online/offline modes.
*   `in/config/experiment/`: Custom YAML files to run specific experiment setups.

### Creating an Experiment Configuration
To specify a new run (e.g., `in/config/experiment/cp_new_run.yaml`):
1.  Add `# @package _global_` at the top of the file.
2.  Override configurations using the `defaults` section:
    ```yaml
    # @package _global_
    defaults:
      - override /env: cartpole
    
    experiment_id: cp_new_run
    group: my_research_group
    total_timesteps: 100000
    online_methods: ppo/cp_tuned
    offline_methods: iql/cp_tuned
    ```
3.  Use `++` in CLI commands to override parameters on the fly:
    ```bash
    python run_pipeline.py cp_new_run ++agent.lr=0.001 ++seed=2
    ```

## 15. Workflow: Local Dev & Cluster Pipeline

To optimize efficiency and avoid wasting compute resources on cluster runs, follow this step-by-step workflow:

### Step 1: Local Sanity Check (Getting Methods Healthy)
Before pushing code or running sweeps, validate that the training methods, callbacks, logging, and dataset-saving loops work correctly using a low-footprint local run:
```bash
# Run a quick local pipeline with overrides to restrict timesteps and evaluation cycles
python run_pipeline.py cp_final total_timesteps=1000 intervals_count=2 eval_episodes=5 local=true save_dataset=false
```
*   **Check**: Make sure no exceptions are raised during online training, dataset buffer saving, and offline evaluation. Ensure the plotter executes cleanly at the end.

### Step 2: Local Hyperparameter Sweeping (Optuna)
Once the method is healthy, perform a local hyperparameter search using the Hydra Optuna sweeper:
```bash
# Run multirun search locally with a specified limit on trials
python run_pipeline.py quick_test -m agent.lr="interval(1e-4, 1e-2)" agent.tau="interval(0.5, 0.9)"
```
*   **Optuna Dashboard**: The sweep automatically launches the Optuna dashboard. Keep track of optimization parameters by visiting `http://127.0.0.1:8080` in your browser.

### Step 3: Cluster Deployment & Remote Execution
Once verified locally:
1.  Submit your runs to the Slurm scheduler using `run_pipeline_slurm.py` or by setting `local=false`.
2.  After execution finishes on the cluster, sync the `results/logs/` and `results/checkpoints/` directories back to your local machine for analysis and plotting.
